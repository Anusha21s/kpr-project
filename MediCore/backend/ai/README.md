# MediCore AI layer (HE-02)

The ML and optimisation layer behind the command centre. It is a **separate
Python service**; the Node backend calls it over HTTP and never imports it. If
this service is down, the hospital system keeps running on its deterministic
operational logic.

Both this service and the models were trained on **synthetic hospital
operations data** (`data/synthetic_generator.py`), because no real hospital
dataset was available to the project. Every response says so.

## Layout

```
ai/
  config.py                 shared constants: pressure bands, feature version, step, disclaimer
  data/
    synthetic_generator.py  the labelled synthetic hospital-operations dataset + stress scenarios
    synthetic/ processed/   generated datasets (regenerated by training)
    features/               prepared per-target feature matrices
    runtime/                rolling live-snapshot history (state_history.jsonl)
  features/
    feature_engineering.py  one definition of every feature, split and target list
  models/<family>/          trained artifacts + <key>_metadata.json (metrics, features, version)
  registry/model_registry.py  version registry: register → gate → promote
  training/                 per-family trainers + train_all.py (the only promoter)
  inference/                live inference services (see below)
  optimization/             OR-Tools CP-SAT optimizers (beds, staff, equipment, theatres, hospital)
  simulation/surge_simulator.py  three-stage what-if projection (never writes)
  recommendations.py        findings, recommendations and event payloads
  evaluation/               reports
  service/app.py            FastAPI surface used by the Node backend
```

## Inference services

| Module | Answers |
|---|---|
| `demand_service.py` | arrivals and queue length, 1 h and 2 h ahead, with a 90 % interval |
| `resource_service.py` | projected utilisation and band for beds, ICU, doctors, nurses, equipment, theatres |
| `surge_service.py` | is the current operational pattern unusual, and how severe is it by policy |
| `pressure_service.py` | pressure band now and one hour ahead, with per-feature contributions |
| `staff_service.py` | per-clinician predicted load and assignment eligibility |
| `equipment_service.py` | projected units needed per category and the projected gap |
| `patient_flow_service.py` | six-hour admissions, discharges, ICU/bed occupancy and theatre backlog |
| `feature_builder.py` | turns a live hospital snapshot into exactly the columns the models were trained on |

`feature_builder.build_live_features` raises rather than silently feeding a model
the wrong shape — training and inference share one feature definition.

## Operating the service

```bash
python3 -m ai.service.app                  # http://127.0.0.1:5001  (npm run ai)
GET  /api/ai/health                        # models, registry, optimizer, disclaimers
POST /api/ai/demand/forecast               # one endpoint per inference service
POST /api/ai/optimize | /simulate | /advisory | /snapshot
```

Successful calls return `{success: true, data}`; failures return
`{success: false, error: {code, message, detail}}`.

## Training

```bash
python3 -m ai.training.train_all          # trains every family, gate-checks, promotes
python3 -m ai.training.train_demand       # a single family
```

* Models only reach `active` through the quality gates (skill vs baseline,
  R², macro-F1) — a model that fails stays `candidate` and the service falls
  back to transparent rules for that target.
* `register()` refreshes metrics and artifacts and preserves lifecycle status;
  `promote()` is the only function that activates a version.
* `FEATURE_VERSION` in `config.py` is stored in every artifact and in every
  prediction. Bumping it deliberately invalidates older artifacts so training
  and inference cannot drift apart.
* `reports/train_all_report.json` lists each model's metrics, the gate result
  and any promotion.

## What this layer never does

It does not diagnose, triage or treat a patient, does not cancel or reschedule
surgery, does not discharge anyone, does not move a patient between beds, and
does not override a clinician's decision. It forecasts operational load and
proposes plans; every plan is advisory and is applied only after a resource
coordinator approves it through the normal workflow.
